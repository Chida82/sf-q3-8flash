## 2. Feasibility (design D4; no GPU; only if 1.5 passes)

- [x] 2.1 Rollback: what verifying up to 8 rows needs for GDN and the KV caches, against the current 3-row path. *(2026-11-20, read from the code, no run. The verify is exact per row today (`verify_rows_exact`: each row computes as a single decoded token, so greedy `--mtp` output is byte-identical to plain) and is capped at 3 rows in a few places: two named snapshots (`snap_*` after row 0, `snap2_*` after row 1) passed as two (buffer, row) pairs to the GDN front, GDN scan and PLE convolution wrappers; `qwen4_graph_fused` (T <= 2, or 3 in a verify); the folded Q2_K down (T <= 3); `qwen4_verify_attention_rows` (`rows[3]`). The attention rows kernels under it are the batched-session ones and already take 64 rows, each with its own key count and block universe. KV and indexer rows past the kept position are overwritten, as today. One recurrent snapshot is 36 layers x 48 x 128 x 128 f32, about 108 MiB, plus the convolution and PLE histories (small). Upstream commit `7e6ab2f` (not in `upstream/main`; `187` took only its lookup index) already extends this verify to 16 rows: n consecutive snapshot slots per layer (`ds4_gpu_qwen4_set_snapshot_rows`), five kernels changed, `tests/test_qwen4_verify_exact.c`, 755 insertions over nine files, and `a4d4804` builds on it. That is the base to port, not new code of this child. Its cost to measure: a block of 8 rows writes 7 snapshots, about 760 MiB of state per cycle; Splash avoids that by taping each row's GDN inputs and folding the accepted path into the state at the next step, which is the fallback if the snapshot traffic shows in the cycle time. Not known until it runs: what an exact row costs from the fourth on. From 1.4, a 2- or 3-row cycle with its predictor step takes about 24-26 ms against 18.2 ms for one row, about 3.5 ms a row; Splash pays about 1.5 ms a row, on batched expert tiles whose result depends on which rows share a tile, which is why its text varies from run to run.)*
- [x] 2.2 Draft weights: a GGUF component through the shared Hugging Face cache (SPEC.md §C), the tensors and their formats. *(2026-11-20. `incoai/Qwen3.8-Flash-Next-DFlash2` at a22a1744 ships `config.json` and one `model.safetensors`, 1150 MiB, 80 tensors, all BF16; no GGUF exists. Tensors: `fc` 2560 x 12800 (62.5 MiB), `hidden_norm`, `norm`; five layers, each q/k/v/o projections (4096, 1024, 1024 x 2560 and 2560 x 4096, 50 MiB), q and k norms of 128, a SwiGLU MLP 2560 -> 7680 -> 2560 (112.5 MiB), two RMS norms, and two dynamic convolutions (`base_kernel` 2 x 2 x 2560, `kernel_projection` 640 x 2560); the selector: two codebooks of 248320 x 256 (121 MiB each) and `hidden_projection` 256 x 2560. Config: block 8, 32 query and 8 KV heads of 128, RoPE base 10000, window 2048, non-causal, top-16 candidates, mask token 248077, target layers 5, 15, 25, 35, 45. Reference code: `z-lab/dflash` `dflash/model.py` (MIT); Splash's `runtime/model/DFlashDraft.cpp` and `kernels/decode/draft.metal` are references only.
